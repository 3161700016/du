Tuesday, Jun 23
现在的各AI在实验室或训练阶段，是否存在“显式学习”？即研究者可以明确地直到AI通过训练或输入规则学到了什么，具体的、可解释的知识？如果存在，可控吗？如果可靠的话，人们应该会这样做对齐？如果不存在，为什么？是哪个过程不允许？或者说，可以通过训练阶段之外的手段实现？
结论先行：  
在当代大模型（LLM、扩散模型等）的训练过程中，并不存在你所说的那种“显式学习”（explicit learning）——即研究者能够明确指出模型在训练中学到了哪条具体规则、哪条知识、哪种可解释的结构，并且能可靠、可控地指定它学习什么。
原因不是“没人做”，而是当前主流训练范式本质上不允许这种显式、可控、可解释的知识注入。

下面我按机制拆解，逐层回答你的问题。

1. 是否存在“显式学习”？——严格意义上：不存在
所谓“显式学习”意味着：

研究者能明确知道模型内部存储了哪些知识

这些知识以可解释、可枚举的形式存在

研究者能指定模型学习某条规则

学习结果可验证、可控

根据现有研究（如 XAI、可解释性综述、可控性研究）显示，深度学习模型仍然是黑箱，其内部知识以高维连续向量形式分布式存储，无法被直接枚举或解释 。

即使是最先进的可解释性方法（logit lens、tuned lens、sparse autoencoder、probing）也只能事后探测模型内部的某些结构，而不能构成真正的“显式学习”机制 。

优化目标是统计拟合，而不是规则学习

知识以分布式方式编码在权重中

没有“知识槽位”或“规则表”

因此：

(1) 模型内部没有“显式规则结构”可供读取
知识不是以“如果 A 则 B”的形式存储，而是以高维特征子空间的形式存在。

(2) 训练过程没有“可控注入点”
你无法告诉模型：“请把牛顿第二定律写入第 123 层第 456 个神经元”。

(3) 训练目标是统计预测，而不是知识表达
模型学到的是“能预测下一个 token 的参数配置”，而不是“知识本身”。

(4) 训练过程不可解释
即使我们知道模型学到了某种行为，也无法追踪它是如何、在哪一层、以什么形式学到的。

3. 如果显式学习可靠，人们会用它做对齐吗？——是的，但它不存在
对齐（alignment）之所以困难，就是因为：

我们无法直接指定模型学习某种价值观

我们无法验证模型是否真的学到了

我们无法控制模型内部的知识结构

这正是为什么对齐研究依赖：

RLHF（人类反馈强化学习）

RLAIF（AI 反馈）

监督微调

规则过滤

结构化提示

机制可解释性（mechanistic interpretability）

而不是“显式写入规则”。

如果显式学习存在，对齐会变得像写程序一样简单：
把价值观写进去即可。  
但现实完全不是这样。

4. 哪个过程不允许显式学习？
关键限制来自三个层面：

(1) 表征层：知识以分布式方式存储
神经网络的知识不是离散符号，而是连续向量空间中的模式。

(2) 优化层：梯度下降无法学习显式结构
梯度下降只会找到能降低损失的参数，而不会形成可解释的结构。

(3) 架构层：Transformer 没有“知识槽位”
Transformer 的注意力头、MLP 层、残差流都不是为“显式知识表达”设计的。

因此，显式学习在当前范式下是结构性不可能的。

5. 是否可以通过训练阶段之外的手段实现显式学习？——部分可以，但不彻底
这里有三条路径：

路径 A：机制可解释性（Mechanistic Interpretability）
目标是把模型内部结构“反编译”为可解释的计算图。
例如：

sparse autoencoder

logit lens

tuned lens

probing

这些方法可以识别某些“特征”、“回路”、“方向”，但仍然无法构成完整的显式知识体系。
它们更像是“显微镜”，不是“编辑器” 。

路径 B：外置显式知识结构（可控）
例如：

工具调用（Toolformer）

外部知识库（RAG）

规则系统（symbolic reasoning）

可编程代理（program-aided LLM）

这些方法把显式知识放在模型外部，让模型调用，而不是让模型内部学习。

这是目前最接近“显式学习”的路线。

路径 C：未来可能的“神经符号混合架构”
例如：

神经网络 + 可微分规则系统

神经网络 + 程序合成

神经网络 + 逻辑推理模块

这些方向试图让模型内部出现显式结构，但目前仍在研究阶段。

6. 总结：为什么显式学习目前不可行？
层级	限制	结果
表征层	知识是分布式向量	无法枚举知识
优化层	梯度下降不产生显式结构	无法指定学习内容
架构层	Transformer 无知识槽位	无法存储显式规则
对齐层	无法验证内部知识	无法做显式对齐


因此，显式学习在当前范式下是结构性缺失的能力。

一、工具调用：Toolformer
1. 简介
Toolformer 是 Meta 提出的一个范式：让语言模型在预训练之后，通过少量示例，自监督地学会何时、如何调用外部工具（API），例如计算器、搜索引擎、翻译系统、日历等。

它的关键点不是“有工具”——而是：调用工具的能力本身被当作一个新任务，写回到语言建模目标里去训练。

2. 原理与技术路线
核心思想：把“调用工具”本身当成一种特殊 token 序列，让模型在继续做 next-token prediction 的同时，顺便学会插入这些调用。

技术路线要点：

工具返回结果被当作普通 token 拼回上下文

模型要学的不是工具内部逻辑，而是：

什么时候需要调用哪个工具

如何构造参数

如何把结果融入后续生成

这本质上是：在语言建模目标上叠加一个“工具使用模式”的分布。

3. 核心步骤（按论文范式）
为每个工具提供少量示例

例如：给出几条“遇到算术问题时如何调用计算器”的示例。

在大规模语料上自动插入候选工具调用

用当前模型在语料中“尝试”插入工具调用（如遇到数字、日期、实体等）。

过滤有用的调用

通过一个评分机制（如看调用结果是否显著降低语言建模损失）筛掉无用或有害的调用。

构造带工具调用的训练数据集

得到大量“自然文本 + 合理工具调用 + 工具结果”的序列。

继续训练模型（自监督）

目标仍然是预测下一个 token，只是现在 token 序列中包含工具调用与结果。

4. 现能达到的效果
显著提升算术、事实查询、翻译等任务的零样本能力，在一些任务上接近或超过更大规模的纯 LLM。

不破坏原有语言能力：因为训练目标仍然是语言建模，只是数据分布被扩展了。

工具可插拔：可以为不同任务挂载不同 API。

从“显式学习”的角度看：

工具本身是显式的（API 文档、功能清晰）。

但“何时调用、如何调用”的策略仍然是隐式编码在权重里。

5. 不足与边界
不足：

调用策略不可解释：我们无法精确说明模型“为什么在这里调用了工具 A 而不是 B”。

工具接口需要人工设计：API 需要结构化、稳定、可被文本描述。

鲁棒性问题：如果工具返回异常、延迟、格式变化，模型可能崩溃或产生幻觉。

安全与对齐问题：工具调用可能触达外部世界（交易、控制系统），需要额外的安全层。

在“显式学习”框架中的位置：

它没有让模型内部变得显式可解释。

它做的是：把“知识/能力”外包给显式系统（工具），模型只学“如何调用”。

这是一种典型的“外置能力 + 内部隐式策略”的混合结构。

二、外部知识库：RAG（Retrieval-Augmented Generation）
1. 简介
RAG（Retrieval-Augmented Generation）是一类架构，而不是单一模型：
在生成前或生成过程中，先从外部文档库检索相关内容，再把检索结果作为额外上下文喂给 LLM。

它的核心目标是：

解决“模型参数中知识过时/不完整”的问题

降低幻觉

让知识更新变成“更新文档库”而不是“重训模型”

LLM 的任务从“直接回答”变成“基于给定材料回答”。

3. 核心步骤（系统视角）
文档预处理与切分

把长文档切成 chunk（如 512–2048 token）。

可能加上标题、元数据。

向量化与索引构建

用 embedding 模型把每个 chunk 映射到向量空间。

构建向量索引（FAISS、HNSW 等）。

把检索结果拼接成 prompt（如“以下是相关资料，请基于此回答问题”）。

LLM 在“显式知识上下文”之上做语言建模。

4. 现能达到的效果
显著降低幻觉率，尤其是事实性问答、企业内部知识问答等场景。

知识可更新、可审计：更新文档库即可更新“知识”；文档本身是可读的。

支持领域定制：法律、医疗、企业文档等。

从“显式学习”的角度：

知识是显式的（文档、条款、表格）。

模型不需要“学会”这些知识，只需要学会如何在给定材料上做抽取、重组、推理。

5. 不足与边界
不足：

检索质量是瓶颈：如果检索不到关键文档，LLM 再强也无用。

长上下文限制：上下文窗口有限，无法塞入太多文档。

多文档推理困难：跨文档、跨段落的复杂推理仍然容易出错。

对齐问题仍在：LLM 仍可能“编造”超出文档的内容。

在“显式学习”框架中的位置：

RAG 把“知识”彻底外置成显式对象。

模型内部仍然是隐式表征，但它不再承担“存储全部知识”的职责。

这是一种非常接近“显式知识系统 + 隐式语言接口”的结构。

三、规则系统：symbolic reasoning
1. 简介
symbolic reasoning 指的是：用符号系统（逻辑、规则、程序、约束求解器）来做推理，让 LLM 只负责：

把自然语言转成符号表示

调用符号推理引擎

把推理结果转回自然语言

典型例子包括：

逻辑定理证明器

约束求解器（SAT/SMT）

规则引擎（if-then 规则）

规划器（PDDL 等）

2. 原理与技术路线
基本模式：

语义解析：
LLM 把自然语言问题转成某种形式化表示（逻辑公式、程序、约束）。

符号推理：
外部引擎在形式化表示上进行精确推理。

结果解释：
LLM 把推理结果转成自然语言答案。

这是一种典型的“神经-符号混合”结构：
LLM 负责“理解与表达”，符号系统负责“精确推理”。

3. 核心步骤（以“规则引擎 + LLM”为例）
定义规则语言与接口

例如：用 Prolog、Datalog、逻辑公式等。

提示 LLM 学会生成规则/查询

通过 few-shot 示例，让 LLM 学会把自然语言转成规则或查询。

调用符号引擎执行

把生成的规则/查询送入外部引擎，得到结果。

结果解释与对话

LLM 把结果包装成自然语言回答，或继续交互。

4. 现能达到的效果
在结构化推理任务上显著优于纯 LLM：如逻辑谜题、约束满足、规划等。

规则可审计、可修改：规则本身就是显式的文本/代码。

适合高可靠性场景：如合规检查、配置验证等。

从“显式学习”的角度：

规则系统本身就是显式知识与显式推理。

LLM 不再需要“学会规则”，只需要“学会翻译与调用”。

5. 不足与边界
不足：

语义解析易错：LLM 把自然语言转成逻辑/规则时可能出错，导致“形式上正确但语义错误”的推理。

规则维护成本高：需要专家维护规则库。

开放世界困难：符号系统擅长封闭世界、精确定义的领域，对开放、模糊、常识性问题不友好。

组合复杂度：规则系统在大规模知识下容易爆炸，需要精心设计。

在“显式学习”框架中的位置：

这是最接近“显式学习”的路线之一：

知识是显式规则

推理是显式过程

但“学习”本身往往不在 LLM 内部，而是：

人类写规则

或用 LLM 辅助生成规则，再由人类审核

四、可编程代理：program-aided LLM（PAL 等）
1. 简介
program-aided LLM（PAL）与更广义的“可编程代理”范式，核心思想是：
让 LLM 生成程序、调用程序、规划行动，把复杂任务拆解为可执行的步骤。

典型工作包括：

PAL：让 LLM 生成 Python 程序来解题，再执行程序得到答案。

ReAct：交替生成“思考（Chain-of-Thought）”与“行动（Action）”，如调用搜索 API。

各类“代理框架”：让 LLM 作为“控制器”，调用工具、记忆、规划器等模块。

2. 原理与技术路线
基本模式可以抽象为：

规划/分解：
LLM 生成一个任务分解或计划（自然语言或伪代码）。

程序/行动生成：
LLM 生成可执行代码或行动指令。

执行与反馈：
外部环境（解释器、API、环境模拟器）执行这些指令，返回结果。

迭代与自反思（在一些框架中）

LLM 根据结果调整计划、修正代码、重试。

3. 核心步骤（以 PAL 为例）
提示设计

给 LLM 示例：如何把自然语言数学题转成 Python 函数。

代码生成

LLM 生成解决问题的代码（通常是纯函数）。

代码执行

在受控环境中运行代码，得到结果。

结果包装

LLM 或系统把结果转成最终答案。

在更复杂的代理中，会加入：

记忆模块：存储中间结果、经验。

工具库：可调用的 API 集合。

控制循环：如“观察 → 思考 → 行动 → 观察 → …”。

4. 现能达到的效果
在需要精确计算、复杂逻辑的任务上表现极佳：因为真正做事的是程序/工具，而不是 LLM 自己。

可审计性强：生成的代码、行动轨迹是显式的，可以检查、重放。

可扩展性好：可以不断增加新工具、新模块，而不必重训模型。

从“显式学习”的角度：

LLM 不再直接“在脑子里算”，而是“写程序让外部环境算”。

程序本身是显式的、可读的、可修改的。

“如何写程序”的能力仍然是隐式学习来的。

5. 不足与边界
不足：

代码正确性问题：LLM 生成的程序可能有 bug，需要测试、约束或验证。

安全问题：执行代码/行动需要沙箱与权限控制。

控制复杂度：多步代理容易陷入循环、无效探索或“自嗨”。

对齐问题迁移：从“回答是否对齐”变成“行动是否对齐”。

在“显式学习”框架中的位置：

它把“复杂推理/操作”外包给显式程序与环境。

LLM 的角色更像是“自然语言编程接口”。

真正的“知识/策略”部分可以逐步迁移到显式程序中（例如：把稳定的策略固化为库函数）。

五、整体视角：这四类技术在“显式学习”问题上的位置
如果把“显式 vs 隐式”画成一个二维图：

横轴：知识/能力是否外置

纵轴：外置部分是否符号化、可编程

大致可以这样定位：

RAG：外置的是“知识”，以文档形式存在，显式但不一定符号化。

Toolformer/工具调用：外置的是“能力”，以 API 形式存在，显式且结构化。

symbolic reasoning：外置的是“规则与推理”，高度符号化、可编程。

program-aided LLM：外置的是“程序与行动”，显式、可执行、可审计。

共同点是：

都绕开了“在模型参数里显式学习知识/规则”这条路。

都把“显式的东西”放在模型外部：文档、工具、规则、程序、环境。

模型内部仍然是隐式表征，但它的职责从“全能黑箱”变成“自然语言接口 + 调度器”。

RAG 的调用是否是 LLM 主动的？

为了让结构清晰，我会把 RAG 的真实机制拆成“表层行为 vs 深层机制 vs 可控性”。

1. RAG 的调用是否是 LLM 主动的？
严格意义上：不是。

RAG 的检索步骤不由 LLM 决定，而是由外部系统（retriever）根据用户 query 自动执行。

流程如下：

Code
用户问题 → 向量化 → 检索 top-k 文档 → 拼接到 prompt → LLM 生成答案
LLM 看到的只是：

Code
[用户问题]
[检索到的文档 A]
[检索到的文档 B]
...
它没有机会说：

“我想再查点别的”

“我觉得这个文档不够”

“我需要换一种检索方式”

除非你构建一个“代理式 RAG”（ReAct / Toolformer / Agent-RAG），让 LLM 可以发出“检索指令”，但那已经不是传统 RAG，而是LLM + 工具调用。

结论：传统 RAG 中，LLM 不主动调用知识库。
它只是被动接收检索结果。

2. LLM 是否能显式判断“我需要回忆什么”？
在传统 RAG 中：不能。

LLM 不知道：

自己的内部知识缺什么

哪些内容应该从外部检索

检索是否成功

是否需要二次检索

它只是看到一个 prompt，然后做语言建模。

如果你希望 LLM 主动判断“我需要查资料”，必须使用：

Toolformer 风格的工具调用

ReAct / Agent 风格的行动规划

Self-Ask / Self-RAG（LLM 自问自答并触发检索）

这些属于“代理式 RAG”，而不是普通 RAG。

3. 调取过程是否“有理有据”？可解释吗？
分两部分：

（1）检索过程：可解释、可控
检索是显式的：

你知道用的是什么 embedding 模型

你知道 top-k 是多少

你知道每个文档的相似度

你知道为什么它被检索出来

这是显式、可审计、可控的。

（2）LLM 使用检索结果的过程：不可解释
LLM 如何使用这些文档：

是否忽略某段

是否误解某段

是否混合内部知识与外部知识

是否产生幻觉

这些都是隐式的，无法解释。

所以：
RAG 的“检索”是显式的，
但“使用检索结果”是隐式的。

4. LLM 能否回写知识库、纠正错误？
默认情况下：不能。

原因：

RAG 的知识库通常是只读的（向量库 + 文档库）

LLM 没有写权限

LLM 也没有“判断知识是否错误”的显式机制

LLM 的输出是文本，不会自动触发写操作

如果你希望 LLM 能“回写知识库”，必须构建一个带写权限的代理系统：

Code
LLM → 判断文档错误 → 生成修正文档 → 写入数据库 → 重建向量索引
但这会带来严重风险：

LLM 幻觉会污染知识库

错误会被永久写入

需要人类审核机制

因此，工业界通常禁止 LLM 自动写入知识库。

结论：
LLM 默认不能回写知识库。
如果允许，也必须加人类审核。

5. 决定“调用什么内容”的元内容是什么？
这是你问得最深的部分。

RAG 的“元内容”来自三个层级：

层级 1：用户 prompt（显式）
用户的问题决定了：

检索 query 的 embedding

检索方向

检索范围

这是最直接的“元内容”。

层级 2：系统提示词 / 模型厂商预置（显式）
例如：

“请基于以下文档回答”

“不要编造超出文档的内容”

“如果文档不足，请说不知道”

这些是系统级元规则，由开发者写死。

层级 3：LLM 内部隐式知识（隐式）
LLM 会根据自身的隐式知识：

判断哪些文档更可信

判断哪些内容更相关

判断如何整合内部知识与外部知识

这些是不可解释的。

6. 总结：RAG 的“显式性”与“隐式性”边界
组件	显式性	谁控制
检索 query	半显式（embedding）	用户 + 系统
检索过程	显式	系统
检索结果	显式	系统
LLM 如何使用检索结果	隐式	LLM 内部权重
是否需要二次检索	隐式（传统 RAG）	LLM 无法决定
知识库内容	显式	人类
LLM 是否能回写知识库	默认不能	系统决定
元内容（调用策略）	用户 prompt + 系统提示词 + LLM 内部隐式知识	三者共同

1. Self-RAG 是否已经有人做？
是的，有，但都不完整。

目前存在三类“Self-RAG”尝试：

（1）Self-Ask / Self-Query / Self-RAG（学术界）
LLM 通过“自问自答”判断是否需要检索，再触发检索。

典型论文：

Self-Ask with Search（Google）

Self-RAG（Meta 2023）

Self-Query Retriever（LangChain）

Chain-of-Verification（CoVe）

这些方法让 LLM：

判断“是否需要检索”

生成检索 query

多轮检索

验证检索结果

但它们仍然是半自主，不是完全自主。

（2）ReAct / Toolformer / Agent-RAG（代理式 RAG）
LLM 通过“思考 + 行动”循环主动调用检索工具。

典型方法：

ReAct（Reason + Act）

Toolformer（Meta）

OpenAI GPT-4 Agents（2023）

LlamaIndex Agent

LangChain Agent

这些方法让 LLM：

主动决定是否检索

主动决定检索什么

主动决定是否继续检索

主动决定是否使用检索结果

但仍然不能自主纠错知识库。

（3）Self-Refine / Self-Consistency / Self-Verification（自我反思）
LLM 自己检查自己的答案是否需要更多信息。

但它们不具备真正的“知识管理能力”。

2. 现有 Self-RAG 能做到什么？
能做到：
判断“是否需要检索”

生成检索 query

多轮检索

过滤不相关文档

验证检索结果

反思“是否需要再查一次”

组合内部知识与外部知识

生成最终答案

不能做到：
判断知识库是否错误

自动纠正知识库

自动更新知识库

长期记忆管理

构建自己的知识结构

跨任务的元学习（meta-learning）

稳定、可靠的检索策略

换句话说：

Self-RAG 目前是“自主检索”，但不是“自主知识管理”。

3. 为什么没有完全实现？
因为 Self-RAG 想做的事情，本质上是：

让一个黑箱模型管理一个显式知识系统。

这会触发三个根本性难题：

（1）LLM 无法显式知道自己“知道什么 / 不知道什么”
LLM 的知识是分布式向量，不是显式符号。

它无法：

列出自己的知识

判断知识缺口

判断内部知识是否过时

判断外部知识是否更可信

这叫 epistemic uncertainty（认知不确定性），目前没有解决方案。

（2）LLM 的检索策略是隐式的，不可解释
Self-RAG 的检索策略来自：

内部权重

prompt

系统提示词

但不是显式规则。

因此：

无法保证稳定性

无法保证一致性

无法保证安全性

无法保证可审计性

这对企业级系统是致命的。

（3）LLM 幻觉会污染知识库（最致命）
如果允许 LLM 自动写入知识库：

一次幻觉 = 永久污染

错误会被索引

检索会不断强化错误

系统会自我中毒（self-poisoning）

甚至可能出现“自我强化幻觉循环”

这是目前所有大厂都不敢做的。

4. Self-RAG 的核心难点（按机制拆解）
我把难点分成“技术难点”和“安全难点”。

技术难点
（1）LLM 无法显式表达“知识缺口”
它只能隐式地“感觉自己不确定”，但不能：

明确指出缺什么

明确指出需要查什么

明确指出查到的内容是否足够

（2）检索 query 生成不稳定
LLM 生成的 query：

可能过宽

可能过窄

可能偏离主题

可能被 prompt 诱导

导致检索质量不稳定。

（3）多轮检索的规划能力不足
LLM 不擅长：

规划检索顺序

判断何时停止

判断是否需要反向检索

判断是否需要验证

（4）无法进行显式知识整合
LLM 无法：

构建知识图谱

合并冲突信息

维护一致性

进行版本管理

安全难点（更关键）
（1）知识库污染风险
LLM 幻觉 → 写入知识库 → 被检索 → 强化幻觉
这是一个正反馈循环。

（2）不可审计性
LLM 的检索策略不可解释，无法审计。

（3）不可控性
LLM 可能：

检索不该检索的内容

写入不该写入的内容

修改不该修改的内容

（4）对齐风险
如果 LLM 能修改知识库，它就能：

修改事实

修改规则

修改价值观

修改系统行为

这会导致对齐崩溃。

5. 为什么业界不放心让 LLM 自主检索/纠错？
因为这意味着：

让一个不可解释的系统管理一个可解释的系统。

这违反了所有工程原则。

工程界的基本原则是：

黑箱不能管理白箱

不可控不能管理可控

不可审计不能管理可审计

不可靠不能管理可靠

Self-RAG 想做的事情是：

让一个不可解释的模型管理一个显式知识库。

这在工程上是不可接受的。
