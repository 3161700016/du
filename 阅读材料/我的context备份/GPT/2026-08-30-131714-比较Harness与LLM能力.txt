有，而且这个问题现在已经有比较直接的实证答案了。

先给结论：

Harness 对 Agent 的实际能力影响可以很大，但它不是一个固定倍率。

在同一模型、同一任务、不同 harness 下，可能出现从“几乎没差”到“巨大差异”的情况。

对当前强模型做长程自主任务，优秀 harness 通常不是把一个模型凭空变成另一个档次的模型；METR 对 GPT-5 / Opus 4.5 的直接对照甚至发现 Claude Code/Codex 相比他们自己的简单 scaffold 没有显著提升。

但在执行效率、token 消耗、上下文管理、失败恢复、工具使用这些维度，harness 可以产生非常巨大的差异；最新 Harness-Bench 和其他 2026 实验已经测到非常夸张的差距。

所以真正合理的比较单位不是 LLM，而是 LLM × Harness × Tools × Environment。

而且这和你之前一直在想的那个问题非常接近：Agent 能力究竟是“脑子”的能力，还是“系统结构”给出来的能力？ 现在的实验越来越明确地表明：两者都是真的，而且作用机制不同。

1. 最硬的一组证据：METR 直接把模型不变，只换 Harness

这是我认为目前最值得看的实验。

METR 在 2026 年专门做了一次：

同一个模型 → 换不同 agent scaffold → 看长期任务能力有没有变化。

他们比较：

Claude Opus 4.5 + ReAct

Claude Opus 4.5 + Claude Code

GPT-5 + Triframe

GPT-5 + Codex

其中：

ReAct 基本就是：

模型 → 工具 → 观察结果 → 模型 → 工具 → …

而 Triframe 已经复杂很多：

advisor 子 agent 制定策略
↓
多个 actor 产生候选动作
↓
多个 rater 比较候选
↓
执行最高分动作

而 Codex / Claude Code 则是各自针对模型优化过的生产级 coding harness。
Metr

结果非常有意思：

没有出现“复杂 harness 碾压简单 harness”的情况。

METR 原文结论就是：

neither Claude Code nor Codex outperform the default scaffolds

而且统计上：

Opus 4.5：Claude Code 胜 ReAct 的 bootstrap 样本只有 50.7%

GPT-5：Codex 胜 Triframe 的 bootstrap 样本只有 14.5%

也就是说，两者差异都没有统计显著性。
Metr

METR 最终直接说：

对 GPT-5 和 Opus 4.5，使用 Codex / Claude Code 对 time horizon 没有很大的影响。

Metr

这个结果非常重要

因为它说明：

“Harness ≠ 自动增加 intelligence。”

你不能简单理解成：

GPT-5 + 复杂 agent framework = 一个比 GPT-5 强很多的“新模型”。

至少对于这类长期软件工程任务，在强模型已经很强的时候，把控制循环做得复杂一点，未必产生多少额外的 reasoning capability。

2. 但是——这绝对不意味着 Harness 不重要

这里恰恰是最容易误解的地方。

METR 测的是一种特定意义的：

这些东西，harness 的影响可能非常大。

3. 更夸张的是：Harness 对“效率”的影响可以达到数量级

还有一篇 2026 年专门研究 coding agent scaffold 的工作，对：

Qwen 3.6 Plus

MiniMax M2.5

在：

Goose

OpenCode

OpenHands-SDK

三个 harness 上进行比较。

他们发现一个非常离谱的东西：

同一个模型，仅仅换 harness，完成一个任务所需要的 token 数可以差到最高约 40×。

但与此同时：

配对的 pass-rate 差异只有 0–8 个百分点。

arXiv

这个结果特别值得你注意。

它意味着：

Harness 很可能不主要改变“会不会”

而改变：

“完成同一个事情，要浪费多少计算。”

比如：

模型本身：

“我知道应该检查 X。”

Harness A：

查 X → 获得结果 → 继续
→ 修复 → 测试 → 完成

Harness B：

查 X
→ 重复查
→ 上下文膨胀
→ 忘了刚才查过什么
→ 又查一次
→ 修改
→ 测试
→ 失败
→ 重新规划
→ 再来一次

于是：

两者最后都能完成。

但：

A: 100k tokens
B: 4M tokens

这时候你说：

“Harness 没有提升 intelligence。”

完全正确。

但如果你说：

“所以 Harness 不重要。”

也完全错误。

因为从实际 Agent 的角度：

B 根本不是一个可用的 Agent。

7. 所以“Harness 能力”有一个非常重要的边界

我会把它分成三层。

层级	Harness 影响	典型效果
把模型原本不会的东西变会	小～中	通常有限
把模型会但经常做不到的东西稳定实现	中～巨大	很重要
扩大模型可以处理的任务长度/状态空间	巨大	长程 Agent 核心

第二、第三层才是真正厉害的地方。

例如模型其实已经知道：

“这个 bug 应该通过运行测试定位。”

但是一次上下文里它：

↓

↓

↓

↓

↓

↓

↓

    retry
↓

    compact
↓

没有增加一丁点参数里的 intelligence。

但是最终：

可能显著提高。

这就是 scaffold effect。

12. 最关键的一句话

所以如果你真正问的是：

“一个一般的 LLM，加一个极其牛逼的 Harness，能不能逼近一个更强 LLM？”

答案是：

能，而且在某些任务上能非常明显。

但是：

它通常不能无限逼近。

因为 Harness 的本质是：

更好地利用已有 capability
	​


而不是：

凭空创造新的 capability
	​


METR 对 GPT-5 / Opus 4.5 的实验正好展示了这个上限：把已经很成熟的 Codex / Claude Code 套上去，并没有把模型的长期能力显著推高。
Metr

但这里其实有一个特别值得你继续挖的坑

我反而觉得你真正关心的不是：

“Harness 有多重要？”

而是：

“一个足够强的 Harness，到底能不能把一个有限 context、有限工作记忆、有限单步推理能力的 LLM，变成一个在能力上远超其裸模型的长期认知系统？”

这就已经不是普通的“agent framework”问题了。

因为一旦 Harness 开始拥有：

persistent memory + retrieval + context compaction + self-reflection + verifier + subagents + branching/forking + external workspace + iterative execution + automatic recovery

9. 但还有一个比“推理步骤”更深的问题：生成前因

你最后一句：

“那么‘前因’就是写 prompt 可以做到的？”

我的答案是：

在“可描述”的意义上，是。

任何一次 LLM 调用：

y=M(x)

其“前因”就是 x。

如果你能构造正确的：

x={goal,state,memory,history,tools,instructions}

那么模型就能产生相应输出。

所以：

causal control of LLM≈context construction
	​


但问题是：

谁构造下一个 prompt？

如果你写死：

Prompt 1
Prompt 2
Prompt 3
...

那只是 workflow。

如果：

LLM → 生成 Prompt 2

那么已经是 meta-reasoning。

如果：

LLM → 生成 Prompt 2 的生成规则

那么开始进入真正的自主认知架构。
