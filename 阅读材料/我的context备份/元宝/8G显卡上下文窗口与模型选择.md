# 8G显卡上下文窗口与模型选择

**用户:**

8G的显卡，不考虑模型大小，不考虑绝对性能，在不爆显存的情况下，最大能启用多长的上下文窗口？又哪些适合本地的模型？

**元宝:**

数据都核对完了。先说结论：**8G 卡的上下文上限不是由显卡决定的，是由模型架构决定的**——选对架构，同一张卡能从 1.5 万 token 跳到 50 万 token，差 30 倍。

## 决定因素：每 token 的 KV 成本

上下文不占权重，只占 KV cache：

```
KV 显存 = 2 × 全局层数 × KV头数 × head_dim × 上下文长度 × 每元素字节数
```

**参数量根本不在这个公式里。** 真正决定你能开多长的是三个架构参数：有几层需要存 KV、每层几个 KV 头、头维度多大。这就是为什么 9B 的 Qwen3.5 能比 8B 的 Qwen3 多塞 14 倍的上下文。

## 8G 卡实测校准表

可用显存按 7.4GB 算（标称 8G 扣掉驱动和桌面合成器占用），已扣 CUDA baseline 与激活开销：

| 模型 | 权重 | KB/token | FP16 KV | INT8 KV | INT4 KV | 原生上下文 |
| --- | --- | --- | --- | --- | --- | --- |
| **Qwen3.5-0.8B** | 1.0G | 12 | 489K | 979K | 1957K | 262K |
| **Qwen3.5-2B** | 2.3G | 12 | 376K | 751K | 1503K | 262K |
| **Qwen3.5-4B** | 3.0G | 32 | 118K | 236K | 472K | 262K |
| **Qwen3.5-9B** | 5.8G | 31.5 | 53K | 107K | 213K | 262K |
| Gemma-4-E2B | 2.8G | \~6※ | 664K | 1328K | 2656K | 128K |
| Gemma-3-4B | 2.4G | 20 | 220K | 440K | 881K | 128K |
| Gemma-3-1B | 0.6G | 4 | 1573K | 3146K | 6291K | **仅 32K** |
| Qwen3-8B（上代） | 4.6G | 144 | 15K | 29K | 58K | 32K |
| Llama-3.1-8B | 4.6G | 128 | 16K | 33K | 66K | 128K |

※ Gemma 4 为保守估算，其 Shared KV Cache 与 unified K/V 的精确 head 配置尚未公开

Qwen3.5-9B 那行我用实测数据校准过：理论公式算出 32 KB/token，第三方实测 32K 时 KV 占 0.98GB、64K 占 1.97GB，反推 31.5 KB/token——**吻合**。

## 为什么 Qwen3.5 是答案

2026 年 2 月的 Qwen3.5 全系换成了混合架构：每 3 层 **Gated DeltaNet**（线性注意力）+ 1 层全局注意力。线性层用固定大小的循环状态替代 KV cache，**内存不随序列增长**；只有 1/4 的层保留 KV，且那些层只有 2-4 个 KV 头。75% 的 KV 开销直接消失。

同理，Gemma 3 靠 5:1 的局部/全局交错（局部层滑动窗口锁死在 1024）把 KV cache 占比从 60% 压到 15% 以下；Gemma 4 更进一步，末尾若干层直接复用前面的 KV。

## 具体推荐

**甜点档（推荐）**：`Qwen3.5-4B` Q4\_K\_M，INT8 KV → **236K**。模型能力足够日常，上下文能吃下整本书。

**极限长度档**：`Qwen3.5-2B` Q4 + INT4 KV → **1M 级**（受 YaRN 官方外推上限 1010K 约束）。适合整仓代码、长文档归档这类"先塞进去再检索"的场景。

**能力优先档**：`Qwen3.5-9B` Q4\_K\_M + INT4 KV → **213K**。9B 在 GPQA Diamond 上打平上代 30B，代价是上下文余量最小。

**只能跑老架构时**：选 `Qwen2.5-7B` 或 `DeepSeek-R1-Distill-Qwen-7B`——它们只有 4 个 KV 头，56 KB/token，INT8 能到 **95K**，比同尺寸的 Qwen3-8B（144 KB/token，仅 29K）强得多。选模型时看 KV 头数，别看参数量。

跑法（llama.cpp）：

```bash
llama-server -m qwen3.5-4b-q4_k_m.gguf -c 262144 -ngl 99 -fa \
  --cache-type-k q8_0 --cache-type-v q8_0
```

## 三个必须知道的坑

**能塞进去 ≠ 能找出来。** 小模型在超长上下文的"大海捞针"检索能力会明显衰减，且超过原生 262K 后必须靠 YaRN 外推，精度继续掉。开 1M 窗口的价值主要在"不用切分"，而不是"每个 token 都被精确记住"。

**Prefill 会成为瓶颈。** 100 万 token 的预填充在 8G 卡上是几十分钟量级的等待，不是"秒开"。长窗口适合加载一次反复提问，不适合频繁重载。

**必须用新版推理引擎。** Gated DeltaNet 是 llama.cpp 内核层的新算子，旧版二进制加载 Qwen3.5 会直接报架构未识别而失败，换任何量化档都绕不过，只能升级。

最后打个假：网上流传的"Qwythos-9B 用 4GB 显存跑 100 万上下文"不成立。按 31.5 KB/token 算，1M 上下文即使上 INT4 KV 也要 7.9GB，加上 5.8GB 权重远超 8G。它确实默认开了 YaRN 的 1M 窗口，但那是**配置值**，不是你这张卡能真正喂满的值。

**用户:**

怎么配置qwen3.5？不一定需要用户友好，只要我的本地agent能调用就行。用什么项目部署？权重从哪下？给一句我的agent自己看完能动手的指令就行

**元宝:**

数据算完了。先说一个反直觉的结论：**在 8G 卡上，Qwen3.5-4B 能开的上下文是 9B 的两倍**——4B 的固定成本只有 3.75GB，能跑满原生 262K；9B 光权重就吃掉 5.8GB，只剩 1.6GB 给 KV，128K 就得上 q4\_0 了。

## 引擎：llama.cpp 的 llama-server

选它的理由是显存控制精度——`--cache-type-k/v` 的 KV 量化和 `-ngl` 的逐层卸载是 Ollama 封装掉、vLLM/SGLang 不做的。8G 卡上这几个开关就是全部余量。另外它原生暴露 OpenAI 兼容 API，你的 agent 不用改代码。

版本是硬门槛：Qwen3.5 的 Gated DeltaNet 算子在 **b8200+** 才有，旧版直接报架构未识别。要 **b8855+**（含 GLM-DSA tokenizer 崩溃修复和 GDN 的 CUDA 优化）。

## 权重

`unsloth/Qwen3.5-4B-GGUF` 的 `Q4_K_M`——Qwen 官方点名的维护方，用 imatrix 校准过，Apache-2.0。别用野路子的转换版。

## 给 agent 的命令

```bash
# 装引擎（预编译 release，别走 apt/brew，那都是陈年老版本）
curl -LsSf https://llama.app/install.sh | sh

# 起服务
llama-server \
  -hf unsloth/Qwen3.5-4B-GGUF:Q4_K_M \
  -c 131072 -np 1 -ngl 99 -fa on \
  --cache-type-k q8_0 --cache-type-v q8_0 \
  --host 127.0.0.1 --port 8080 --log-disable
```

起了之后就是标准 OpenAI 端点：

```python
from openai import OpenAI
c = OpenAI(base_url="http://127.0.0.1:8080/v1", api_key="none")
c.chat.completions.create(model="qwen3.5-4b", messages=[...])
```

`-c 131072` + `q8_0` 总占用 5.75GB，离 7.4GB 还有余量。想要满原生 262K 就把 `-c` 提到 `262144` 并把 cache-type 换成 `q4_0`，占用一样是 5.75GB。

## 四个会让 agent 跑歪的坑

`-c`** 是总上下文，会被 **`-np`** 均分。** 开 `-np 4` 时每个槽位只分到 `-c/4`。单 agent 场景务必显式 `-np 1`。

`-fa on`** 和 KV 量化是绑定项。** 不开 flash attention 时 llama.cpp 每次注意力计算都要把 KV 反量化回 float，比不量化还慢。

**thinking 模式要看型号。** Unsloth 文档明确说 Qwen3.5 小模型默认禁用思考，但你的 agent 框架若自动注入 `enable_thinking`，会凭空多出一大段输出 token。要锁死就加 `--chat-template-kwargs '{"enable_thinking":false}'`。

**视觉塔在白白吃显存。** Qwen3.5 是原生多模态，Unsloth 的 GGUF 把视觉编码器嵌在主文件里，纯文本 agent 用不上却照占几百 MB。目前没有干净的跳过开关，只能按上面已经计入的占用数去配 `-c`。

## 什么情况下该换 9B

如果你的 agent 做的是复杂多步推理而不是长文档吞吐，9B 在 GPQA 上打平上代 30B，那个提升比上下文长度值钱。代价是上下文砍到 128K 且必须 `q4_0`：

```bash
llama-server -hf unsloth/Qwen3.5-9B-GGUF:Q4_K_M \
  -c 131072 -np 1 -ngl 99 -fa on \
  --cache-type-k q4_0 --cache-type-v q4_0 \
  --host 127.0.0.1 --port 8080
```

总占用 6.80GB，已经贴着安全线了——再往上加会开始踩到桌面合成器的显存波动。
