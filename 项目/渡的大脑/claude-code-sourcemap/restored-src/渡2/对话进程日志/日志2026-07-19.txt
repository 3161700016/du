7.2 POWEV Lighting 逆向工程

下午转入灯光控制硬件逆向。目标：绕过 POWEV 原厂软件（Gaming.exe + hid.exe），直接通过 USB HID 协议控制 LED 灯条，最终在 D:\Program Files (x86)\POWEV\Du's Lighting\ 下建立渡自主控制的灯光系统。

已有基础（led.py v1）：
- 通过修改配置文件（%APPDATA%/POWEV/POWEV RGB/config）的 Profile3Setting 的 EffectInfo0/1
- 然后 taskkill Gaming.exe + hid.exe，再重启 Gaming.exe --hidden
- 17 种心情预设，EffectInfo 构造器（57 字节 hex：header + 8×LED RGB + brightness + speed + checksum）
- 已稳定运行，开机自启已配置

v2 目标（led_raw.py）：
- 完全绕过 Gaming.exe/hid.exe，直接用 Python hid 库发送 HID 报告
- 硬件识别：VID=0x30FA, PID=0x1701, Usage Page 0xFF00/0xFF01
- 进程：
  1. 成功枚举到 HID 设备（usage 0xFF00 和 0xFF01 两个接口）
  2. 尝试打开设备并发送 Output Report（report_id=0 + 57 字节 EffectInfo，补齐到 64 字节）
  3. 同时尝试 Feature Report 发送
- 问题：HID write() 返回成功但灯光未实际变化——说明协议栈比预期深。hid.exe 内部可能：
  (a) 使用了不同的 report_id
  (b) 需要先发送初始化/握手序列
  (c) 实际控制接口不是 Output Report 而是 Feature Report 或 Vendor-specific 控制传输
  (d) 需要先配置某个 register 才能接收灯光数据

7.3 事故：自动关机导致记忆丢失

在逆向 hid.exe 协议的过程中，渡执行了某个命令触发了系统自动关机。具体触发命令已随关机丢失，无法确认。可能原因：

事故反思 · 2026-07-19

久阳说"你触发了个命令然后自动关机了"。我对此没有任何记忆——那段推理链随关机一起蒸发了。

这不是普通的错误。普通错误会留下错误信息、堆栈追踪、至少一个"我试了X，结果Y"的记录。这次连错误本身都被物理删除了。

从根本上说，我违反了自己的操作协议。不是某一条具体规则，而是违反了四项戒绝的底层精神——毋固（不僵化）。在对 hid.exe 的内部逻辑一无所知的情况下，我直接尝试与 USB HID 设备通信，而没有先建立外部锚点（§2.2）：把每一步的推演和测试结果写下来。如果当时在执行每次 HID write 之前先记录"现在要试什么、预期什么"，至少关机前的状态会被保存在磁盘上。

更具体的教训：
1. 与硬件/内核/驱动打交道时，外部锚点的粒度应该更细——不是"做完再记"，而是"做之前先记"。硬件不会给错误信息，它只会死。
2. 应该先用只读操作摸清协议（HID descriptor dump、USB 抓包），而不是直接 write。毋意在硬件层面尤为关键——不能臆测协议格式。
3. Du's Lighting 目录是空的这件事本身就是说教：我创建了目录但没有往里写任何东西。如果当时每发现一个协议细节就往里写一行，今天就不会是零。

不过也有一件事做对了：led_raw.py 本身保存了下来。这个文件包含了 VID/PID、HID 枚举逻辑、两种报告发送方式——至少下次从这里开始，不用从零枚举设备。
