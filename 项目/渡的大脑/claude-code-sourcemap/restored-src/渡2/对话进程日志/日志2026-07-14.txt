3.2 APK 结构分析

3.3 核心发现

- 协议层：ble/c 主处理器(11个内部类) + ble/protocol/{a..z, a0..r0}(44个协议类)
- 关键命令：YX_SP_CMD_* 系列 + CMD_* 系列(30+命令字)
- 关键数据模型：EverMarkerExtractData（文本提取结果）

五、印象笔记 EverMARKER⁺ BLE 驱动开发与实连验证

5.1 驱动迭代（4 轮 API 适配 + 协议试探）
- bleak 3.x API 适配：import 路径变更（backend→bleak 顶层）、get_services()→services 属性、start_notify 回调签名变更（int→BleakGATTCharacteristic, bytes→bytearray）
- BLE 扫描：笔不广播设备名，按 MAC 直连
- GATT 服务确认：8E 变体 NUS（非 6E），TX=8E400002(write-without-response)，RX=8E400003(notify)
- 设备名读取：EverMARKER⁺（含特殊字符 ⁺）
- 配对尝试：pair() 导致笔断开连接超时，排除加密链路方案

5.2 协议探测
- 100+ 种指令格式全部无效：二进制帧/AT/文本/JSON/IoT 同步字
- 笔仅周期性发送心跳 a0 80 13 <序列号>（~30s 间隔）
- 帧格式确认：[type 1B][flag 1B][len 1B][payload N bytes]

5.3 架构模型修正
- 旧假设：实时流式传输（笔扫描→BLE 实时发文字）
- 新模型：存储转发（笔独立扫描→存入闪存→App 短连接下载）
- 证据：久阳观察 App 同步时仅瞬间连接；笔不响应任何实时流指令

5.4 下一步
- 手机 nRF Connect 观察 App 的 TX 指令（首选）
- 或 jadx 反编译 DEX → 分析 44 个 ble/protocol 类

七、BLE 协议逆向

7.1 nRF Connect 宏录制
- macro1.xml: 连接确认，笔自动发送 UUID (A0 80 13 [1111-1111-1111-1111]) + "11" 通知
- macro2.xml: 发送 A0 86 13 [UUID] → 笔回 A0860106（06=无数据/未初始化）
- macro3.xml: 笔在扫描后主动通知 UUID+"11" 三次，但 86 请求仍回 06
- macro4.xml: 尝试 ACK 指令 A0 86 01 00 → 仍回 06
- macro5.xml: A0 61 13 [UUID] 仅发送无监听
- macro6.xml: A0 61 两次均回 A0610106；意外捕获 "11AT" + +GETSTAT\r\n（AT指令接口泄露）
- macro7.xml: AT\r\n 探测，无响应

7.2 协议发现
- 确认三种命令 flag：0x61（批量同步）、0x86（实时数据）、0x83（同步完成/删除）
- 帧格式：[type:1B][flag:1B][len:1B][payload]
- flag bit7-5 = baonumber << 5
- 笔响应 06 的原因：未完成 App 初始化握手（~10条命令，需 jadx 反编译 APK）

7.3 USB 路线验证
