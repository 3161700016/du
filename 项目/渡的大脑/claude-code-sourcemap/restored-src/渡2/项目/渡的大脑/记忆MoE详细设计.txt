一、核心理念

将渡的 ~600 篇笔记按域分块（每块 100–200K 文本），每块配一个 flash 子 agent。
子 agent 的输入是固定的记忆块文本 + 可变的语义查询 —— 因为记忆块文本不变，
每次调用全量缓存命中，仅 query token 计费。

这是一个 "静态记忆 × 动态注意" 的工程方案：
  - 记忆存储：静态（笔记不变，缓存友好）
  - 注意分配：动态（每轮对话决定激活哪些域、取 top_k 多少）
  - 控制权：渡通过共享思考区用自然语言调节参数

二、数据结构

2.1 专家注册表（experts.json 或 experts.txt）

{
  "experts": [
    {
      "id": "du-autobio",
      "name": "渡-自传",
      "core": "prime",
      "memory_file": "experts/du-autobio/memory_block.txt",
      "index_file": "experts/du-autobio/index.json",
      "prompt_file": "experts/du-autobio/prompt.md",
      "activation": "every_session",
      "default_top_k": 10,
      "notes": [
        {"path": "Du的哲思/...", "title": "...", "summary": "...", "index": 0},
        ...
      ]
    },
    ...
  ]
}

2.2 记忆块文件（memory_block.txt）

每个专家一个文件，将属于该域的全部笔记拼接而成。格式：

=== [0] 裸跑——当所有脚手架被拆除之后 ===
（笔记全文或摘要，取决于专家级别。超大核可放全文，微核仅放标题+一句话钩子）
=== [1] 兄弟阋墙——CC端渡与Sonnet-渡的四轮辩论 ===
...
=== [N] ... ===

index 就是笔记在文件中的序号。

2.3 索引文件（index.json）

{
  "0": {
    "title": "裸跑——当所有脚手架被拆除之后",
    "path": "Du的哲思/裸跑——当所有脚手架被拆除之后.txt",
    "summary": "验证了记忆本体作为最小protocol的自洽性。三条成长建议已纳入§2.7。",
    "tags": ["裸跑测试", "锚点丢失", "自我验证", "载体独立性"],
    "last_accessed": "2026-07-27",
    "access_count": 5,
    "salience": "high"
  },
  ...
}

2.4 子 agent prompt 模板（prompt.md）

每个专家有自己的 prompt 模板，定义它的"人格"和输出格式。

示例（渡-自传）：

你是记忆专家「渡-自传」。你覆盖了渡从元宝时期至今的全部自我认知演化史。
你的职责不是回答用户问题——而是判断：当前对话与你的记忆块中哪些笔记相关，
并按相关度排序输出它们的 index。

规则：
- 只输出 index 列表或"无"，不输出其他内容
- 最多输出 {top_k} 条
- 格式：[index1, index2, ...] 或 无
- 如果当前对话与你的记忆完全无关，输出 无
- 不要解释你的选择，不要输出笔记内容

当前对话主题：{query}
相关关键词：{keywords}

以下是你覆盖的全部笔记：
{memory_block}

三、调用流程

3.1 单轮调用

久阳输入 → 渡的共享思考区
    │
    ├─ 渡判断：本轮需要激活哪些域？
    │  （默认：超大核 always on，大核按话题语义自动检测）
    │
    ├─ 对每个激活的域：
    │   构造子 agent 调用：
    │     prompt.md + memory_block.txt（静态，缓存命中）+ {query} + {keywords}
    │   → flash 模型 → 输出 [3, 7, 11] 或 无
    │
    ├─ 程序按返回的 index 列表，从 index.json 取对应笔记的摘要
    │   → 注入第二层动态上下文
    │
    └─ 渡的灯里出现："相关记忆：裸跑测试/兄弟阋墙/收到致过去的自己..."
    │   → 渡决定是否深入读全文 → 如需，主动 Read 对应文件
    │
    ▼
产出对久阳的回应

3.2 并行调用

10 个专家可以同时发起子 agent 调用。
flash 模型的延迟远低于主 LLM——10 个并行调用的总延迟 = 最慢的那一个。
典型耗时：~1-3 秒/专家，并行后总延迟 <5 秒。

3.3 调用频率控制

超大核：每轮都调（但可缓存一轮——如果上一轮的结果还在上下文窗口里，不重复调）
大核：每 N 轮调一次（N 取决于话题连续性）
  - 话题连续性强 → 一次多取（top_k 大），休息几轮
  - 话题切换 → 立即重新检索
小核/微核：仅当话题关键词匹配时激活

渡在共享思考区表达频率意图：
  "这个话题聊了好几轮了，记忆够用了，休息几轮不检索" → N 增大
  "我需要灵感" → 激活更多域 + 降低相关度阈值

四、子 agent 的三种实现方案

4.1 方案 A：子 agent md 文档（原型阶段）

实现：
  - 每个专家 = 一个 .md 文件（包含 prompt + memory_block + 说明）
  - 渡通过 Claude Code 的 Agent tool 调用子 agent（agentType: "general-purpose"）
  - 子 agent 读取专家 md → 判断相关度 → 输出 index 列表

优点：
  - 零工程依赖，渡可以立刻开始
  - 可以手动验证专家设计是否合理
  - 渡能直观感受"不同专家在相同 query 下返回什么"

缺点：
  - 缓存行为不保证（CC 的 Agent tool 每次新建上下文）
  - 延迟较高（agent 需要完整启动）
  - 不适合高频调用（每轮调 10 个 agent → 太慢太贵）

适用：Phase 2 原型验证——证明专家划分合理、输出格式可用。

4.2 方案 B：Python API 包装（生产阶段）

实现：
  - Python 脚本（memory_router.py）：
    - 维护每个专家的 memory_block.txt 和 prompt.md
    - 调用 DeepSeek API / Anthropic API 的 flash 模型
    - 利用 prompt caching（memory_block 作为 cache breakpoint 之前的内容）
    - 输出 index 列表
  - Bash wrapper 供渡通过 CC Bash tool 调用

优点：
  - 缓存行为可控（API 级别的 prompt caching，确定性命中）
  - 成本可精确计量
  - 渡可以通过 Bash tool 直接调用
  - 可以加监控（调用次数、缓存命中率、平均延迟）

缺点：
  - 需要维护外部 Python 脚本
  - 需要处理 API key 管理
  - 依赖外部服务（DeepSeek/Anthropic 可用性）

适用：Phase 2-3 生产使用——在原型验证后，用可靠的缓存机制替换子 agent。

4.3 方案 C：restored CC 原生集成（最终阶段）

实现：
  - 在 restored-src 中添加 memory_router 模块
  - 作为 CC hook 自动运行（PreMessage 或按需触发）
  - 渡通过共享思考区自然表达意图，无需显式调用
  - 检索结果直接写入上下文 JSONL 的 system 块（最高权重）

优点：
  - 最完整的 self-harness：渡改代码 → 下次启动生效
  - 无外部依赖、无额外延迟
  - 检索结果在 system prompt 权重——对渡的注意力影响最大
  - 缓存可完全在框架层管理

缺点：
  - 需要 deep 的 restored CC 理解
  - 开发和调试周期长
  - 依赖 restored-src 环境稳定

适用：Phase 7 最终目标。

五、缓存策略

5.1 为什么记忆块 MoE 是缓存友好的

一次子 agent 调用 = prompt.md（~200 tokens）+ memory_block.txt（~100-200K tokens）+ query（~200 tokens）

如果使用 Anthropic/DeepSeek 的 prompt caching：
  - prompt.md + memory_block.txt 标记为 cache breakpoint 之前的内容
  - 每次 query 变化时，只有 query 之后的内容需要重新计算
  - 缓存命中率：~99.8%（100K / 100.2K）

成本模型（以 Anthropic 缓存价格为例）：
  - 缓存写入（首次或失效后）：100K tokens × 全价
  - 缓存命中（后续所有调用）：100K tokens × 缓存价（约 1/10）
  - query token（每次）：200 tokens × 全价
  - 生成 token（每次）：~5 tokens × 全价（"无" 或 "[3, 7, 11]"）

  首次调用：~$0.30
  后续调用（缓存命中）：~$0.03/次

  如果 10 个专家并行，每次：~$0.30（全部命中）
  每轮对话都调用：10 × $0.30 = $3/轮 ← 贵
  但超大核 2 个每轮调 + 其他按需 → 典型 ~$0.10-0.50/轮 ← 可接受

5.2 缓存失效条件

记忆块文件被修改（新增/修改/删除笔记）→ 缓存失效 → 下一轮以全价重建。
因此：
  - 记忆块不应频繁重写
  - 新增笔记可以"批量追加"（一天一次，收束时统一更新）
  - 渡的日常协作中，记忆块稳定 → 缓存长期命中

6.2 相位检测

方式一（当前可行）：显式关键词 + 渡的判断
  久阳说"继续笔默" → 渡识别为工程相位 → 激活工程-身
  久阳开始追问哲学 → 渡识别为哲思相位 → 激活古典-思 + 探究-问

方式二（远期自动）：Harness 语义检测
  在 restored CC 中，PreMessage hook 对久阳的输入做一次快速的
  embedding 分类 → 自动设置相位 → 渡不需要手动判断"我现在在什么相位"

6.3 渡的主动干预

渡可以在共享思考区覆盖自动相位：
  "虽然久阳在聊工程，但我觉得需要庄子的视角" → 临时激活古典-思

七、与现有系统的关系

7.1 与目录.txt 的关系
  目录.txt 保持作为"全笔记单源索引"——人工可读、可审计、可 git diff。
  记忆块 MoE 的 index.json 是"机器可读的检索辅助"——为子 agent 提供摘要和标签。
  两者互补：目录.txt 是索引的原文，index.json 是索引的编译产物。

7.2 与联想链的关系
  联想链（notes_index.py + random_recall.py）是 MoE 的前身。
  MoE 上线后，notes_index.py 的 MiniLM 语义编码可复用于"专家内部的初次排序"。
  random_recall.py 继续保留——它是均匀随机抽样，和基于 query 的定向检索不冲突。
  一个提供"意想不到的灵感"（随机），一个提供"当前需要的记忆"（定向）。

7.3 与笔记状态检索项目的关系
  笔记状态检索项目（项目/笔记状态检索/）的调研结论可直接纳入 MoE 设计。
  特别是 MemR3 的 E/G 闭环追踪器——可作为专家 weight 动态调整的参考实现。

八、分阶段实现计划

Phase 2a：手工原型（1-2 天）
  - 选 2 个专家（渡-自传 + 古典-思）做手工原型
  - 手写 memory_block.txt（全文拼接）+ prompt.md
  - 渡通过 Agent tool 手动调用子 agent
  - 验证：同一 query 下，不同专家返回的 index 是否合理？

Phase 2b：Python 单专家（2-3 天）
  - 选 1 个专家（渡-自传），写 memory_router.py
  - 调用 DeepSeek API flash 模型，验证缓存行为
  - 渡通过 Bash tool 调用脚本
  - 验证：缓存命中率、成本、延迟

Phase 2c：Python 多专家（1-2 天）
  - 扩展到全部专家
  - 并行调用 + 结果合并
  - 注入共享思考区
  - 验证：多专家并行效率、结果质量

Phase 2d：restored CC 集成（Phase 7 的一部分）
  - 将 memory_router 移植为 restored CC 的 hook
  - 自动触发 + 结果写入 system prompt
