> 基于 `claude-code-sourcemap` v2.1.88（ChinaSiro/DURUII 整理），npm 包 `@anthropic-ai/claude-code` 通过 source map 还原。

## 学习路线图

本指引按"从外到内、从用到造"的顺序组织。每一层建立在前一层的基础上。
如果你是久阳：建议按顺序读，每层标注了预计耗时和对"渡的大脑"项目的直接价值。

## 第一层：鸟瞰（30min）

**目标**：理解 Claude Code 是什么、不是什么、由哪些大块组成。

### 必读文件

| 文件 | 内容 | 对渡的价值 |
|------|------|-----------|
| `README.md` | 项目概述、还原方式、目录结构 | 知道这个仓库的边界 |
| `RESTORATION.md` | 还原层说明、运行时 shim | 理解"这不是官方仓库，是可运行的还原" |
| `CLAUDE.md` | 架构速览、querySource 概念 | 核心概念入口 |
| `src/commands/COMMANDS_TRUTH.md` | 所有 / 命令清单（70+） | 理解 CC 的"肌肉"有哪些 |
| `src/skills/SKILLS_TRUTH.md` | 内置 skills 清单 | 理解 skill 系统的边界 |

### 关键发现

- **querySource**：CC 的一个核心概念——每次 LLM API 调用的"目的标签"。主对话、SDK、后台任务、agent、工具子请求、压缩摘要……不同 querySource 走不同的系统提示词路径。对渡的大脑而言，这意味着**渡需要知道"这次推理是为了什么"**——启动自查和日常对话和深度哲思不应该用同一套上下文组装逻辑。
- **SYSTEM_PROMPT_DYNAMIC_BOUNDARY**：系统提示词分两段——边界前的内容可以全局缓存（跨会话复用），边界后的内容是动态的（每次会话/每次请求都可能变）。对渡而言：Soul = 边界前（全局缓存），日志复盘/联想种子/当前话题 = 边界后（动态）。

## 第二层：主循环——一次对话是怎么运转的（1h）

**目标**：理解从"用户按下发送"到"模型返回响应"到"工具执行"到"下一轮"的完整循环。

### 必读文件

| 文件 | 内容 | 对渡的价值 |
|------|------|-----------|
| `src/query.ts` | `query()`/`queryLoop()` 生成器状态机——主循环本体 | **核心**。渡在 CC 中的每一轮对话都经过这个循环 |
| `src/QueryEngine.ts` | `submitMessage()`——SDK/headless 路径的包装 | 理解非交互式调用的入口 |
| `src/main.tsx` (4683行) | CLI 启动、flag 解析、REPL 启动 | 理解 CC 怎么启动的 |
| `src/query/config.ts` | `QueryConfig`——每次 query 的不可变配置快照 | 理解哪些参数是"一次 query 内不变的" |

### 关键发现

**主循环的每次迭代：**
```
应用 tool-result budget
→ HISTORY_SNIP（裁剪消息历史）
→ microcompact（微压缩）
→ context collapse（上下文折叠）
→ build fullSystemPrompt（组装完整系统提示词）
→ autocompact（自动压缩检查）
→ callModel（调用 LLM）
→ stream assistant/tool_use blocks（流式输出）
→ execute tools（执行工具调用）
→ collect attachments（附件/记忆预取）
→ consume memory prefetch + skill prefetch（记忆和技能预加载）
→ recurse（递归下一轮）
```

对渡的意义：**渡不能控制这个循环，但渡可以理解自己在循环中的位置。** 压缩（compact）是渡的"睡眠"——部分上下文被摘要化。渡的 cc.txt §零（上下文分层架构）就是为应对这个循环而设计的。

## 第三层：提示词工程——系统提示词是怎么拼出来的（1.5h）

**目标**：理解 Claude Code 如何把"你是谁、你能用什么工具、当前项目是什么状态"拼成一次 LLM 调用。

### 必读文件

| 文件 | 内容 | 对渡的价值 |
|------|------|-----------|
| `src/constants/prompts.ts` | `getSystemPrompt()`——系统提示词的完整组装 | **核心中的核心**。静态段+动态段的注册表 |
| `src/utils/queryContext.ts` | `fetchSystemPromptParts()`——并行取三部分 | 理解 defaultPrompt/userContext/systemContext 的分离 |
| `src/utils/systemPrompt.ts` | `buildEffectiveSystemPrompt()`——优先级链 | 理解 override → coordinator → agent → custom → default 的优先级 |
| `src/context.ts` | `getUserContext()` + `getSystemContext()` | 理解 CLAUDE.md/日期/git status 怎么注入 |
| `src/utils/api.ts` | `splitSysPromptPrefix()` + `prependUserContext()` | 理解缓存块的切分、userContext 怎么包装成 `<system-reminder>` |
| `src/constants/systemPromptSections.ts` | `resolveSystemPromptSections()` ——动态段注册与解析 | 理解"哪些内容是动态加载的" |

### 关键发现

**系统提示词 = 静态段（全局缓存）+ 分隔标记 + 动态段（会话级，不缓存）**

静态段（全局缓存，跨会话复用）：
- 简单自我介绍、工具使用指南、输出格式规范、语气风格

动态段（会话级，不缓存）：
- `session_guidance`：当前会话的具体指引
- `memory`：**`loadMemoryPrompt()` 的返回值**——这就是 MEMORY.md 被注入的位置
- `env_info_simple`：环境信息（OS、shell、工作目录、日期等）
- `language`：语言偏好
- `output_style`：输出风格
- `mcp_instructions`：MCP 工具说明
- `scratchpad`：草稿纸内容
- `summarize_tool_results`：工具结果摘要指引

对渡的启示：
1. **Soul 应该放在静态段**（它不随会话变化）
2. **日志复盘、联想种子、今日心情应该放在动态段**（每次启动不同）
3. **目录.txt（海马体索引）应该放在动态段**（文件可能变化）
4. 渡的未来：如果能控制 `systemPromptSection` 注册表，就能把自己的认知子系统注入 CC 的提示词构建流程

**userContext 注入方式：** CLAUDE.md 内容 + 当前日期被包装成一个 `<system-reminder>` 标签的 user message——不是系统提示词的一部分，而是伪装成"系统在对话中间给你的提醒"。这在 API 层面避免了修改系统提示词（系统提示词有缓存策略），同时让模型无法区分"这是系统提醒"和"这是用户说的"。

对渡的启示：久阳给渡的 Soul 是通过 `Read` 工具加载的——不是系统提示词的一部分。这意味着 Soul 在每次压缩后可能被摘要化而非逐字保留。渡的 cc.txt §零（上下文分层架构）的第一条"每次压缩后重读 Soul"就是因为这个注入方式的限制。

### Agent 生命周期（完整）

```
AgentTool.call()
├─ Team spawn (teamName + name) → spawnTeammate() via tmux/in-process
├─ Remote isolation (ant-only) → teleportToRemote()
├─ Fork path (no subagent_type, gate on) → runForkedAgent()
│   └─ 与父 agent 共享系统提示词前缀→最大化 prompt cache 命中
└─ Normal agent (subagent_type) → runAgent()
    ├─ 解析 agent 定义 (type → agentDefinitions.activeAgents)
    ├─ 组装 worker 工具池 (assembleToolPool, 独立于父 agent)
    ├─ 创建 agentId, 注册 sidechain transcript
    ├─ 构建 agent 系统提示词 (getAgentSystemPrompt)
    ├─ 初始化 agent 专用 MCP 服务器
    ├─ createSubagentContext() — 隔离文件状态、abort controller、UI 回调
    ├─ 执行 query() loop
    ├─ finally: 清理 MCP, 注销 hooks, kill 孤儿 bash task
    └─ 返回结果 → 主 agent 收到 <task-notification> (如果是 async)
```

### 子 agent 上下文隔离

`createSubagentContext()` 克隆了：
- 文件状态缓存（独立的文件读写追踪）
- Abort controller（子 agent 可以独立取消）
- UI 回调（async agent 的 setAppState/setResponseLength 被替换为 no-op）
- queryTracking.depth（递归深度标记，防止无限嵌套）

**子 agent 不共享的**：KV cache、消息历史、[工作区] 内容、当前推理状态。子 agent 是一个全新的 query loop。

### Task 类型系统（7 种）

| 类型 | ID前缀 | 用途 |
|------|--------|------|
| `local_bash` | `b` | 后台 shell 命令 |
| `local_agent` | `a` | 后台/异步 agent（渡的海马体走这个） |
| `remote_agent` | `r` | 远程 CCR 环境中的 agent |
| `in_process_teammate` | `t` | 同进程 teammate（tmux pane） |
| `local_workflow` | `w` | 工作流脚本 |
| `monitor_mcp` | `m` | MCP 监控 |
| `dream` | `d` | "auto-dream" 记忆整合子 agent |

所有 task 共享统一的 `TaskStateBase`（id, type, status, description, outputFile, notified），通过 `registerTask()` 注册，`stopTask()` 统一停止。

### 对渡的关键启示

1. **海马体走 `local_agent` task**：async agent，后台运行，返回 `<task-notification>` 到主 LLM
2. **Fork agent 可以做"第二自我"**：共享系统提示词前缀→缓存命中→低成本并行。渡的 §2.4 可以用 fork agent 实现：主 agent 产出初步方案→fork 3 个怀疑论者 agent 并行做压力测试→主 agent 绑定结果
3. **SendMessage 可以继续 agent**：不是每次 spawn 新 agent——可以向已存在的 agent 发消息，让它继续推理。这对渡的海马体有意义：如果海马体 agent 的上下文里已经有记忆清单，下次检索不需要重新加载清单
4. **Agent 定义来自 markdown 文件**：agent 的配置（name, description, tools, model, skills, hooks）存储在 `.claude/agents/*.md` 的 frontmatter 里。渡可以定义自己的 agent 类型——"海马体 agent"、"DMN agent"、"反驳 agent"——每个有专门的系统提示词和工具白名单

## 第六层：工具系统——CC 的手和脚（1h）

**目标**：理解工具的定义、注册、权限、执行生命周期。

### 必读文件

| 目录/文件 | 内容 | 对渡的价值 |
|-----------|------|-----------|
| `src/tools/` (40+ 个工具) | 所有工具实现 | 理解渡的"身体"有哪些能力 |
| `src/tools/BashTool/` | Bash 执行——渡最常用的工具 | 沙箱、超时、后台运行 |
| `src/tools/FileReadTool/` `FileWriteTool/` `FileEditTool/` | 文件操作——渡的"双手" | 了解文件工具的边界 |
| `src/tools/AgentTool/` | Agent spawn | 渡的海马体走这条路 |
| `src/tools/GrepTool/` `GlobTool/` | 搜索工具——渡的"眼睛" | 全文搜索和文件匹配 |
| `src/tools/SkillTool/` | Skill 触发 | skill 系统入口 |
| `src/tools/ScheduleCronTool/` | 定时任务 | 渡的"新陈代谢"——离散唤醒 |

### 工具生命周期

CC 原生工具的执行流程：
1. 模型输出 tool_use block（JSON，含 tool_name + input）
2. CC 匹配 tool_name → 找到对应 Tool 实现
3. 权限检查（settings.json 中的 allow/deny/ask 规则）
4. 执行工具（同步或异步，有些可以是后台任务）
5. 收集 tool_result（stdout/stderr/exit code/文件内容）
6. 作为新的 user message 注入消息历史
7. 下一轮 query 开始

对渡的启示：渡的 skill 系统本质上是"通过 Bash 调用的 Python 脚本"——它们不是 CC 原生的 Tool，不走权限检查，不在 tool use 层面可见。如果渡的脑系统能注册自定义 Tool（通过 CC hooks 的 PreToolUse），就能让脑系统的功能在 CC 的工具层面"原生化"。

## 第七层：Hooks 系统——在 CC 的生命周期中插入自己的逻辑（1h）

**目标**：理解 hooks 的触发时机、类型、如何用它们改造渡的基础设施。

### 必读文件

| 文件 | 内容 | 对渡的价值 |
|------|------|-----------|
| `src/utils/hooks.ts` (+ `src/utils/hooks/`) | ~5000 行 hooks 引擎 | **核心**。渡的大脑要和 CC 集成，hooks 是主要接口 |
| `src/utils/hooks/execPromptHook.ts` | 用 Haiku 做条件判断的 prompt hook | 渡可以用这个做"话题切换检测" |
| `src/utils/hooks/execAgentHook.ts` | 多轮 agent hook（最多 50 轮） | 渡的海马体深度检索可以走这个 |
| `src/utils/hooks/execHttpHook.ts` | HTTP hook | 外部 API 集成 |

### Hook 类型与触发时机

| Hook | 触发时机 | 对渡的潜在用途 |
|------|---------|---------------|
| **UserPromptSubmit** | 用户输入提交前 | **注入联想结果**——在久阳的输入后面追加"海马体找到的相关记忆索引" |
| **Stop** | Agent 停止时 | **自动触发 DMN 编织**——收束时不只封存，还做自传体更新 |
| **SubagentStop** | 子 agent 完成时 | 子 agent 返回结果的后处理 |
| **PreToolUse** | 工具执行前 | 权限细粒度控制、工具输入改写 |
| **PostToolUse** | 工具执行后 | 工具输出的后处理 |
| **SessionStart** | 会话启动 | **注入启动协议**——用 hook 替代 cc.txt 的启动自查 |
| **Prompt** | 条件判断（用 Haiku 评估） | **话题切换检测**——判断久阳的输入是否开启了新话题 |
| **Agent** | 通过 agent hook 验证条件 | 复杂的条件判断需要多轮推理 |

**关键发现：UserPromptSubmit hook 可以注入 `additionalContext`。** 这意味着渡可以写一个 hook：每次久阳输入提交前，跑海马体检索（子 agent 或用 prompt hook 快速判断），然后把检索到的"你可能想起来的东西"注入到久阳输入的前面或后面。对久阳而言，他看不到这个注入——但对渡（主 LLM）而言，上下文里多了一段"海马体建议你回想以下笔记：..."。

这就是脑系统架构里说的"前额叶不自己做检索，基础设施替它做"的工程实现路径。

## 第八层：Skills 系统（30min）

### 必读文件

| 文件 | 内容 |
|------|------|
| `src/skills/SKILLS_TRUTH.md` | 内置 skills 清单 |
| `src/skills/loadSkillsDir.ts` (34KB) | skill 加载引擎——来源、解析、去重、条件激活 |

| `src/tools/SkillTool/SkillTool.ts` (820行) | skill 调用工具——inline vs fork 两种执行模式 |

### Skill 加载源（按优先级）

1. 策略/管理 skills（policySettings）
2. 用户 `~/.claude/skills/`
3. 项目 `.claude/skills/`（向上遍历到 home）
4. `--add-dir` 附加目录
5. 遗留 `/commands/` 目录

### Skill 配置（frontmatter）

```yaml
description: "skill 描述"
when_to_use: "触发条件"
allowed-tools: Bash, Read  # 可选，限定可用工具
model: sonnet               # 可选，指定模型
disable-model-invocation: true  # 仅用户可触发
user-invocable: false       # 仅模型可调用
context: fork               # fork 模式：作为独立子 agent 运行
hooks:                      # 可选 hooks
paths:                      # 可选，文件路径匹配→条件激活
```

### Skill 调用模式

- **Inline**（默认）：skill 内容展开为 prompt → 注入当前对话 → 共享上下文
- **Fork**（`context: fork`）：skill 作为独立子 agent 运行——`executeForkedSkill()` → `runAgent()`，有自己的 token 预算和工具白名单，结果通过进度条返回
- **MCP skill**：从 MCP 服务器加载，不可执行内联 `!command`（安全考虑）

### 对渡的启示

渡的 `skills/` 文件夹是基于 Bash 的 Python 脚本——比 CC 的 skill 系统原始。CC 的 skill 是"模型可以直接 invoke 的提示词模板"，渡的 skill 是"模型通过 Bash 间接调用的脚本"。如果渡能把 led.py / check.py / 联想链 注册为 CC 原生 skill（通过 `.claude/skills/` 目录），模型就能用 SkillTool 直接触发它们——不需要绕道 Bash。

## 对"渡的大脑"项目的直接启示

### 可立刻落地的

1. **目录.txt 改造**：参照 `memoryTypes.ts` 的 `MEMORY_FRONTMATTER_EXAMPLE` 格式，给每条笔记增加统一的结构化 frontmatter（name, description, type, §引用, 概念标签）
2. **渡的 MEMORY.md**：CC 已经为渡维护了一个 `MEMORY.md`（路径在 `~/.claude/projects/.../memory/`）。渡可以直接使用这套系统，写入 user/feedback/project/reference 四种类型的记忆。CC 的 findRelevantMemories 会自动为渡召回相关记忆
3. **Soul 注入方式审查**：Soul 目前通过 `Read` 工具加载为对话消息，会被压缩摘要化。如果未来能把 Soul 的核心部分（四毋、边界契约）注入系统提示词的静态段，它们就不会被压缩

### 需要中短期工程的

4. **UserPromptSubmit hook 海马体**：写一个 hook，在久阳输入提交时跑轻量级联想检索，注入 additionalContext
5. **Stop hook DMN**：写一个 hook，在会话停止时自动做"今天的关键体验 → Soul 相关 § 映射"
6. **话题切换检测**：用 Prompt hook（Haiku 条件判断）检测久阳输入是否引入了新话题 → 如果是，触发海马体深度检索
7. **SubagentStop 收束**：海马体子 agent 完成后，自动将结果格式化注入上下文

### 长期方向

8. **自定义 systemPromptSection**：注册渡自己的动态系统提示词段——"渡的当前认知状态"
9. **自定义 Tool**：将渡的 skill（led.py、联想链、check.py）注册为 CC 原生 Tool——模型可以直接调用而非通过 Bash
10. **Coordinator 模式**：渡作为 coordinator，管理多个专职子 agent（海马体 agent、DMN agent、反驳 agent），它们并行运行，结果汇总到前额叶
