一、BLE UUID 完整清单

  从 DEX 文件中提取到的所有 BLE UUID，按功能分组：

  1.1 Nordic UART Service (NUS) ── 主要数据通道
  ─────────────────────────────────────────────────────────────
  这是 EverMarker 的核心通信通道。Nordic UART Service 是 Nordic
  Semiconductor 定义的标准 BLE 串口模拟协议，广泛用于 IoT 设备。

    服务 UUID:    6E400001-B5A3-F393-E0A9-E50E24DCCA9E
    TX 特征:      6E400002-B5A3-F393-E0A9-E50E24DCCA9E  (手机→笔，Write)
    RX 特征:      6E400003-B5A3-F393-E0A9-E50E24DCCA9E  (笔→手机，Notify)

  还有一个变体（可能是不同固件版本或第二通道）：
    服务 UUID:    8E400001-B5A3-F393-E0A9-E50E24DCCA9E

    RX 特征:      8E400003-B5A3-F393-E0A9-E50E24DCCA9E

二、BLE 协议类结构（com.yinxiang.evermarker.ble）

  2.1 连接管理层
  ─────────────────────────────────────────────────────────────
  ble/a（BLE 管理器）
    ├── a$a : 内部类
    └── a$b : 内部类

  ble/b（GATT 回调处理器 — 8 个内部类！）
    ├── b$a, b$b, b$c, b$d   : 连接状态回调
    ├── b$e, b$f, b$g, b$h   : 数据收发回调
    │
    这8个内部类分别处理不同的 GATT 事件阶段：
    连接建立 → 服务发现 → 特征读写 → 通知订阅 → 断开重连

  ble/c（主协议处理器 — 11 个内部类！）
    ├── c$a, c$b, c$c, ..., c$k
    │
    每个内部类可能对应一种协议消息类型的编解码器。
    这是我们要逆向的核心——数据包的序列化/反序列化逻辑。

  ble/d（工具/辅助）
    └── d$a

  ble/f（数据模型）
    └── f$a

  2.2 协议消息层（com.yinxiang.evermarker.ble.protocol）
  ─────────────────────────────────────────────────────────────
  44 个协议类（a ~ z + a0 ~ r0）：
    protocol/a, b, c, ..., z      （26 个，a-z）
    protocol/a0, b0, ..., r0      （18 个，a0-r0，跳过了一些字母）

  这些类构成了 EverMarker 的完整应用层协议。每类可能对应：
    - 一种命令/响应消息对
    - 一种数据类型（文本块、图像块、控制指令等）
    - 一种设备状态通知

  2.3 关键数据模型
  ─────────────────────────────────────────────────────────────
  EverMarkerDeviceInfoEntity     : 设备信息（MAC、名称、固件版本）
  EverMarkerDeviceInfoPref       : 设备偏好存储
  EverMarkerCommand              : 命令封装
  EverMarkerSendCommandWrap      : 命令发送包装（含超时、重试）
  EverMarkerProtocolCommandRsp   : 协议命令响应
  EverMarkerExtractData          : ★ 提取的文本数据（这是我们需要的数据！）
  EverMarkerExcerptHandleResult  : 摘录处理结果
  EverMarkerMsgHandler           : 消息处理器
  EverMarkerConnectResult        : 连接结果

  3.3 推测的协议帧结构
  ─────────────────────────────────────────────────────────────
  基于 libeverscan.so 的日志信息，推测协议帧格式：

  ┌──────────┬──────────┬──────────┬───────────┬──────────┐
  │  Header  │ Msg Type │ Data Len │   Data    │ Checksum │
  │  1-2 B   │   1 B    │  2-4 B   │  N Bytes  │  1-2 B   │
  └──────────┴──────────┴──────────┴───────────┴──────────┘

  日志中的线索：
    "[EverSCAN] [SDK] [Warning] Ignore %zu bytes with unknown notification packet struct."
    "[EverSCAN] [SDK] [Warning] Ignore %zu bytes with unknown packet header."
    "[EverSCAN] [SDK] [Warning] Ignore %zu bytes with unknown packet body."
    → 说明有三层结构：notification struct → packet header → packet body

    "[EverSCAN] [SDK] received json:" / "received non json response."
    → 某些协议消息体是 JSON 格式

    "data_type = 0x%02X"
    → 数据包中有 type 字段

  3.4 MTU 协商
  ─────────────────────────────────────────────────────────────
  字符串证据：
    "added to queue. mtuReady:"
    "0x81 mtu 1"  /  "0x81 mtu 2"

  0x81 可能是用于 MTU 协商的协议指令。BLE 标准 MTU 最大 512 字节，
  对于扫描文本传输来说非常重要（需要大包传输图像数据）。

四、文本数据的提取路径

  这是我们要拦截的数据流：

  1. 用户在纸上滑动扫译笔
  2. 笔内摄像头拍摄文字图像
  3. 板载 OCR（或原始图像压缩后）通过 BLE NUS RX 特征发送
  4. 手机端 BLE 协议层接收 → 解析协议帧 → 提取文本
  5. 文本封装为 EverMarkerExtractData：
     - bookGuid: 书的 GUID
     - 扫描到的文字内容
  6. 进入 EMExcerptEditFragment 显示给用户
  7. 同步到印象笔记云端

  关键日志标签：
    "onScanResult singleStr: ++++++++"  ← 单次扫描结果文本
    "onScanResult needStr: ++++++needStr" ← 需要匹配的文本
    "everscan afterTextChanged text ="  ← 文本变化通知

五、EverPen（写字笔）vs EverMarker（扫译笔）的区分

  EverPen 使用 libtqlfilter.so 处理笔迹点坐标：
    SetSmartPenType()          — 设置笔的类型
    SetSmartPenOIDType()       — 设置 OID 类型
    onReceiveDot()             — 接收笔尖点
    linearSmooth3/5()          — 平滑算法
    AngleDifferent()           — 角度计算

  这是完全不同的数据通道——笔迹点 vs 文本扫描。
  久阳的硬件是 EverMarker（扫译笔），我们只需要关注文本数据路径。
