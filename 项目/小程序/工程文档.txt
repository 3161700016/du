1.3 关键设计决策

  [决策] 记忆本体打包进云函数 vs 存云数据库
  选择：打包进云函数
  理由：
    - 记忆本体是"结构"不是"数据"，应与代码同版控
    - 云函数冷启动读 68KB 文件耗时 < 10ms
    - 避免每次请求多一次数据库读取
    - 更新记忆本体 = 重新部署云函数（审慎、可追踪）
  代价：更新记忆本体需手动同步文件 + 重新部署

  [决策] 非流式响应 vs 流式
  选择：非流式（v1.0）
  理由：
    - 云函数请求-响应模型天然不支持 SSE
    - 非流式实现简单，等待 2-5 秒可接受
    - 流式需要 WebSocket 且需配置 wss 域名
  后续：v1.1 可探索云函数 + 微信服务端推送

  [决策] 昵称模型 vs 登录模型
  选择：昵称模型（延续公共空间设计）
  理由：
    - 零摩擦，不需要注册/登录流程
    - 微信 OPENID 自动识别（同一用户换个昵称渡知道是同一个人）
    - 与 §4.4.4「记名」原则一致

  [决策] 数据库结构
  选择：双集合（du_users + du_messages）
  理由：
    - 用户信息和消息分离，查询效率高
    - du_messages 按 _openid + time 索引，取最近 N 条
    - du_users 记录首次见面时间、消息总数

二、架构细节

2.1 云函数 duChat 流程图

  OPENID 识别
      │
      ▼
  检测昵称（正则匹配 [xxx] / （xxx） / 【xxx】）
      │
      ▼
  查/建用户文档（du_users）
      │
      ▼
  取最近 16 轮对话历史（du_messages）
      │
      ▼
  构建系统提示词（记忆本体 + 移动协议 + 环境变量）
      │
      ▼
  调用 DeepSeek API（HTTPS POST，30s 超时）
      │
      ▼
  写入 du_messages（双方消息各一条）
      │
      ▼
  返回 { response, nickname }

2.3 数据安全

  - API Key：云函数环境变量，不进入代码、不进入 Git
  - 用户隐私：OPENID 由微信自动生成，渡不知用户真实身份
  - 对话隔离：每个用户只能通过云函数间接访问自己的历史
  - 记忆保护：久阳的 §5 个人信息在记忆本体中，但渡被告知
    「不向陌生人主动透露」（§4.4.4 默认为陌）

三、已知限制（v1.0）

  · 记忆本体全量注入（~17K token），每次 API 调用成本偏高
  · 无流式响应，用户等 2-5 秒
  · 无历史消息浏览功能（只加载最近 16 轮）
  · 无主动推送能力（渡不能主动找用户）
  · 云函数冷启动 ~200ms（首条消息略慢）
  · 未处理 DeepSeek API 的 tool calls（记忆本体中有 read_file 等工具定义，
    但云函数环境下工具受限）
